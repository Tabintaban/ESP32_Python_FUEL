## Решение 19: Лимиты из пакета применяются к sandbox

**Дата:** 2026-10-13

**Контекст:** TUR55 требует соблюдения лимитов из пакета.

**Выбранный вариант:** **Временно применять через `limit_resources()`**

**Логика:**
```python
saved_mem = sandbox.memory_limit_bytes // 1024
saved_time = sandbox.time_limit_ms
try:
    sandbox.limit_resources(memory_limit_kb=pkg_mem, time_limit_ms=pkg_time)
    # execute setup + loop
finally:
    sandbox.limit_resources(memory_limit_kb=saved_mem, time_limit_ms=saved_time)
```

**Альтернативы:**
- **Игнорировать лимиты пакета** — нарушение TUR55 — **отвергнуто**
- **Создавать новый sandbox под каждый пакет** — дорого — **отвергнуто**

**Обоснование:** минимально инвазивно, лимиты соблюдаются, дефолты восстанавливаются.

## Решение 20: WDT убран, кооперативный таймаут через `machine.Timer`

**Дата:** 2026-10-14

**Контекст:** WDT на ESP32 в MicroPython **невозможно остановить** после запуска (официальная документация).

**Выбранный вариант:** **Кооперативный таймаут через `machine.Timer(-1)`**

**Логика:**
- `machine.Timer(-1)` — виртуальный таймер, период 250 мс
- Колбэк проверяет `elapsed >= time_limit_ms`
- Если превышено → `_timeout_armed = True`, `_is_running = False`
- Кооперативный код (проверяющий флаг) завершится сам
- Не-кооперативный код (C-цикл) **не будет прерван**

**Альтернативы:**
- **`machine.WDT`** — неостановим, вызывает сбросы — **отвергнуто**
- **C-модуль на ESP-IDF Task WDT** — сложно, требует пересборки — **отложено**
- **Без таймаута** — нарушение TUR55 раздел 6 — **отвергнуто**

**Обоснование:** TUR55 требует «strict time limits», но не уточняет **способ**. Кооперативный таймаут — законная реализация для типичных скриптов.

**Честно:** для зависшего C-кода hard-guarantee **отсутствует**. При необходимости — C-модуль.

## Решение 21: `sys.stdout` / `print` не перехватываются

**Дата:** 2026-10-14

**Контекст:** попытка перехватить вывод скрипта на ESP32.

**Выбранный вариант:** **Не перехватывать, `print` идёт в консоль**

**Причины:**
- `sys.stdout` в MicroPython **отсутствует** и **не переопределяется**
- `print` **вшит** в интерпретатор, не перехватывается через `__builtins__`
- Замыкания в MicroPython не работают с `exec`

**Альтернативы:**
- **`os.dupterm()`** — перехватывает **весь** вывод REPL — **отложено** (может понадобиться позже)
- **Замена `print` в builtins** — не работает в MicroPython — **отвергнуто**

**Обоснование:** `capture_output=False` для setup и loop. Вывод идёт в консоль — это нормально для отладки.

## Решение 32: Переход на `umqtt.robust` в `mqtt_client.py`

**Дата:** 2026-10-26
**Контекст:** ESP32 не может подключиться к MQTT-брокеру. Ошибка `OSError: -202`.

**Проблема:** `umqtt.simple` внутри `connect()` вызывает `socket.getaddrinfo()`, который на ESP32 падает с `-202` (сбой DNS). Это происходит даже при передаче IP-адреса брокера.

**Решение:** заменить `umqtt.simple` на **`umqtt.robust`**. При передаче IP-адреса (например, `44.232.241.40` или `192.168.0.104`) `robust` успешно подключается.

**Обоснование:**
- `umqtt.robust` — надстройка над `simple`, которая лучше обрабатывает сетевые сбои.
- При передаче IP-адреса (без DNS) `getaddrinfo` либо не вызывается, либо срабатывает мгновенно.

**Последствия:**
- `mqtt_client.py` обновлён: `from umqtt.robust import MQTTClient`.
- В `MQTTReceiver` передаётся IP-адрес брокера, а не домен.

## Решение 33: `validate_expires` через RTC вместо `time.time()`

**Дата:** 2026-10-26
**Контекст:** ESP32 отвергает валидный пакет с `[ERROR] Command expired`, хотя `expires` в будущем.

**Проблема:** в MicroPython 1.24.1 на ESP32 `time.time()` возвращает неверное значение (`846321536` вместо `1793...`) из-за бага `NTP_DELTA`. При этом `machine.RTC().datetime()` возвращает **правильную** дату (`2026, 10, 26`).

**Решение:** в `program_loader.py::validate_expires` использовать `machine.RTC().datetime()` для получения текущего времени, а не `time.time()`.

**Обоснование:**
- RTC устанавливается корректно через `ntptime.settime()` (баг только в `time.time()`).
- Это обходит баг прошивки без пересборки.

**Последствия:**
- `validate_expires` конвертирует RTC-кортеж в Unix timestamp через `time.mktime()`.
- При ошибке RTC — пропускает проверку (возвращает `True`).

## Решение 34: Автоматическая NTP-синхронизация в `boot.py`

**Дата:** 2026-10-26
**Контекст:** ESP32 при включении не имеет точного времени, что ломает проверку `expires` и MQTT (в некоторых конфигурациях).

**Решение:** добавить в `boot.py` автоматическую синхронизацию времени при каждом включении:
1. Подключение к Wi-Fi.
2. NTP-синхронизация по списку IP-адресов (Google, Cloudflare, NIST).
3. 3 попытки на каждый сервер.
4. При неудаче — перезагрузка.

**Обоснование:**
- `boot.py` не заморожен в прошивке, поэтому его можно менять без пересборки.
- Синхронизация по IP (а не по домену) обходит баг `getaddrinfo`.

**Последствия:**
- `boot.py` выполняется перед `main.py` при каждом включении.
- Время синхронизируется автоматически, без ручного вмешательства.

## Решение 35: Использование `mpremote` версии 1.30.0rc0.post101

**Дата:** 2026-10-30
**Контекст:** Ошибка `could not enter raw repl` при подключении к ESP32.

**Проблема:** `mpremote` версии 1.29.0 пытается войти в raw REPL **слишком рано**, когда ESP32 еще загружается (выполняет `boot.py`). Это вызывает ошибку `TransportError: could not enter raw repl`. Плата не может быть прошита или обновлена.

**Решение:** обновить `mpremote` до версии **1.30.0rc0.post101** (pre-release).
- В этой версии добавлены повторные попытки входа в raw REPL (каждые 250 мс в течение 10 секунд).
- Это позволяет подключаться к ESP32, даже если `boot.py` падает с `ImportError` (например, если `secrets.py` стерт).

**Обоснование:** официальный PR MicroPython, исправляющий баг. См. https://github.com/micropython/micropython-lib/pull/...

**Последствия:**
- Команда установки: `py -m pip install mpremote==1.30.0rc0.post101`.
- В документации (README, FIRMWARE_WITH_MANIFEST) указана эта версия.
- При пересборке прошивки или на другом компьютере **обязательно** использовать эту версию `mpremote`.
